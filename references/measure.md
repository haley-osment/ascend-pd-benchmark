## 预热与缓存

同 case 同并发预热，纯 D 和完整 PD 预热也要走完整输出。记录预热条数、观察到的并发和是否正常完成。少量串行短请求只够探活。改变长度、并发或服务配置后，用新负载预热。正式的请求数、时长、QPS 都从正式轮起算。

- Cache0 在预热排空后清 P/D prefix cache，核对成功，再取正式轮起始计数。沿用基线的缓存开关和输入策略。结束核对两个有效端点；如果禁用缓存导致无查询计数，注明禁用状态和零命中证据。
- Cache90/100 先清理前一轮遗留缓存，再按原生数据预填目标公共部分。90% 场景只预填该公共部分；把正式数据整批预跑后直接保留，可能把独有后缀也预热。100% 纯 D 则要预填完整重复前缀。先探针验证，排空探针和预填请求，再截取正式计数。
- 对同一端点同一计数范围，命中率 = 正式轮 Δhits / Δqueries；多个独立实例用计数增量求和后相除，避免重复统计同一批请求。检查计数单位、重启归零和其他业务流量。P 本地前缀、D 本地前缀和 D 外部 KV 命中分别记录。无计数、无查询、未采到记原因；不能据此填实测 0%。原生 100% 重复可以只测到 98%～99%，报告实测值并检查差距。

## 对齐与统计

- 同构/异构对比固定模型、脚本、数据、并发、请求数、入口、缓存、输出和统计范围。通常分清 101P+104D UB、101P+104D UBoE、212P+104D UBoE。对比前两组可观察同机器换链路；同时换卡型和链路的对比只能说明组合表现。MBTS、镜像或 runner 变化均应注明；判断单因素影响时固定其他条件。
- 完整 PD 对齐纯 P 时，先读取同模型、同组网、同长度与命中率下的纯 P **全程平均 TTFT**。完整 PD 保持 1K 输出，从用户给的 CC 或相邻有效档起跑，根据实测升降 CC，逐档记录 TTFT、命中和 QPS。偏差 = (PD TTFT / 纯 P TTFT − 1) × 100%。历史对齐补测常用 `data_num=9×CC`；DSV4.1 的一轮常规补测为 4×CC，GLM 纯 D 用过 3×CC。先用本次要求或同类基线。容差及停止点沿用当前任务；用户选定一档即停止，报告实际偏差。
- 临时验证各配置默认一个正式轮次。专门检查纯 P 稳定性时默认三轮。需要多轮时，优先让单轮正式压测控制在约 10 分钟内；固定请求数、长上下文等与此冲突时说明预计耗时。两边要变更样本量时保持对齐。参考表的样本数可能只是入选稳态条数，实际发压数以原始配置和明细为准。
- 热态描述预热情况，稳态描述统计窗口。核对每个 case 实际保存的 AISBench 模式（如 `default_perf`、`stable_stage`），外层脚本可能逐 case 改写。默认报告完整正式轮；复现参考窗口时同步列出入选数/正式总数和选择依据。如果一边只入选 9 条、另一边有数百条，保留原始稳态值，并从请求时间戳统一计算全程作对照。对旧数据重算只记录为重算。
- 服务端健康、进程存活和第一条请求成功都不足以标记完成。检查发送/接收数、最后进展时间、服务 running/waiting、P/D 日志和失败记录。对话断开后先看远端 PID、driver 日志及报告；积压或超时先找哪个阶段停滞，再决定是否重试。记录无效轮原因，保留有效轮；取消的 case 跳过。

## 怎么解释差距

先确认分子分母（异构/同构，或完整 PD/同组网纯 P）、输出长度、实测缓存命中、在途并发和窗口。闭环下可用平均在途数 / 平均 E2E 秒近似核对 QPS。输出从 1 增到 1024 会延长并发槽位占用；缓存命中从 90% 降到 87% 会增加未命中 token。分别检查 P 排队/prefill、KV 交付、D 排队/decode 和代理时间。P 端命中不能证明 D 已收到 KV。缺少阶段证据时写明未决原因。

性能基线关闭 profiling。需要算子分析时另开同负载采集轮，按用户指定的 torch profiler 配置，在目标窗口通过 `/start_profile`、`/stop_profile` 触发，核实 P/D、rank、起止时间、产物可在 MindStudio 打开。按轮单独存入用户指定目录（历史为 `D:\profilerData`）。链路系统采样、整卡 HBM/LLC 计数和算子 trace 各自说明采集范围。多 rank 有重叠，算子时长求和不能当作端到端关键路径；旧模型或异常尖峰不能证明当前模型的某算子带宽饱和。

验证模型是否进入某个算子分支时，把加载 `sitecustomize.py`、`sys.monitoring` 或 Python 行级回调的服务作为诊断实例。记录命中的 rank 和输入形状后，从启动环境移除探针，重启被观测的服务并按相同负载预热，再测正式 QPS 和 TTFT。仅停止打印或只记录首个命中，仍应通过无探针复测核对开销。

## 多卡 profiling 交付与验收

1. **保留原始目录结构。** Ascend PyTorch Profiler 导出完成后，把同一轮、同一采集窗口的各 rank 完整 `*_ascend_pt` 目录复制到同一个父目录。保留原目录名、`profiler_info_<rank>.json` 和 `ASCEND_PROFILER_OUTPUT/` 下的数据库等产物。不同轮次或窗口分别存放。把多份单卡 DB 平铺到一个目录，可能导致 MindStudio 的 Card Filter 只列出一张卡。
2. **核对本地副本。** 按实际采集的主机和 rank 清点目录。对 DB 格式，核对 `profiler_info_<rank>.json`、数据库 `RANK_DEVICE_MAP` 中的 rank 与设备映射，以及复制前后各主库的 SHA-256。多机时按主机核对设备号，同一物理卡号可以出现在不同主机上。
3. **给对导入入口。** 多卡对比时，新建 MindStudio 工程并导入这些 `*_ascend_pt` 的共同父目录；单卡时间线可直接导入对应的 `ASCEND_PROFILER_OUTPUT/ascend_pytorch_profiler_<rank>.db`。回复里给出实际路径和本轮预期卡号。
4. **在 Timeline 验收。** 查看各 Host 的 Card Filter 是否列出全部预期卡号，并切换卡号检查目标泳道。若筛选框只有一张卡，先检查导入层级和分卡目录是否完整；若之前只复制了散放的 DB，从原始采集位置补齐目录后重新导入，通常无需重采。无法打开界面时，分别说明已完成的文件校验和待确认的界面结果。
